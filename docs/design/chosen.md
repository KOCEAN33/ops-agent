# Chosen

The owner's decisions. Each item names what was chosen and what was rejected.

- **Role: operator, not engineer**: the agent contains an incident and hands off the cause. It protects, in order, data, then security, then service, and may stop a service that threatens the cluster. A manifest change, a resource limit included, belongs to the owner, who takes the issue. Rejected: HolmesGPT as the base, because it carries investigation through its own scripts and analysis further than a first responder needs, and its approval flow targets Slack.
- **Long-running and conversational**: a Deployment that holds one session per alert group and continues it when the owner replies in the alert's Discord thread. Rejected: one `claude -p` run per alert on CI runners, because it ends before the owner can answer.
- **Owner channel**: Discord only, through threads and approval buttons. The bot posts a starter message in one configured channel and opens the alert group's thread on it. The thread's name is the alert group plus a short title of the problem the model records with the issue summary, such as `KubeJobFailed / example-app: backup job runs out of memory`, so the owner can tell threads apart later. The name is fixed when the thread opens. The bot reaches Discord through `@discordjs/core`, `@discordjs/ws` and `@discordjs/rest`. Rejected: the alert group alone as the name, because it does not say what went wrong; the alert's `summary` annotation, because it repeats the rule's text instead of what the model found; renaming the thread as the diagnosis changes, because Discord allows two renames per 10 minutes and a moving name is harder to find; a dedicated web front end, because Discord already carries the alerts, the conversation and the buttons; a thread on Alertmanager's own message, because finding that message means matching titles that carry stranger text; a hand-written gateway client, because a silent disconnect would cut the owner channel unseen.
- **Provider-neutral**: the loop calls models through the Vercel AI SDK, which reaches Anthropic directly, OpenRouter, and OrcaRouter, the last two through the OpenAI API. Anthropic is paid from the owner's monthly API credit. Rejected: a subscription token from `claude setup-token`, because Anthropic's terms cover "ordinary, individual usage" and say nothing on unattended runs; pi-ai, because the SDK reaches all three providers through maintained packages.
- **Runtime**: TypeScript on Bun, in this public repository, separate from the owner's data. The loop, session store and context compaction are built here, not inherited from Claude Code.
- **Trigger**: every alert with severity `warning` or `critical` starts or resumes a session.
- **Stopgap autonomy**: the agent acts without approval only when its own PromQL reads show a cluster-wide threat: a node pressure condition held for 2 minutes, a node NotReady for 5 minutes, or shared storage at 90% used, or at 80% used and on a 6-hour trend that fills it within 6 hours. The 80% floor keeps one short write burst on a mostly empty volume from starting a stop. Every other stopgap waits for the owner's approval button in the thread. The threat test reads only metrics the agent queried, never alert annotations or log text, so injected text cannot start a stop. Code, not the model, also picks an autonomous stop's target (Autonomous targets). Rejected: full autonomy, because a misread or injected stop takes a service down unseen; approval for every stop, because the cluster goes unguarded while the owner sleeps.
- **Stopgap actions**: scale a Deployment or StatefulSet to zero, suspend a CronJob, delete a Pod so its controller restarts it. Each keeps the PVCs and one reverse action undoes it, so the worst case of a wrong stop is downtime. The agent does not undo its own stopgap: the issue records the undo, and the owner approves it in the thread.
- **Stoppable namespaces: an allowlist**: a namespace is stoppable only once the owner adds it, so a new application stays protected until then. The allowlist never holds a namespace that stores or backs up data for others, such as the shared database and its operator, or one that runs the platform: the GitOps controller, secret sync, monitoring, storage drivers, `kube-system`, and the agent's own. When the database is under threat, the agent stops the applications writing to it, never the database. The allowlist lives in the deployment, outside this repository. Rejected: a denylist, because a new platform component missing from it would be stoppable.
- **Autonomous targets: an opt-in label**: in an allowlisted namespace, a workload is a candidate for an autonomous stop only when its manifest carries the `stoppable` label. The label key carries a prefix whose domain the deployment sets, takes one exact value, and is read from the live Deployment, StatefulSet or CronJob, never from a pod. Code measures each candidate's share of the threat with PromQL, such as its memory on the pressured node or its writes to the filling volume, and stops the largest above a minimum share of 20%. That value is unmeasured (`docs/candidates.md`). Share comes only from kubelet, cAdvisor and node-exporter series, since an application's own metrics can carry labels it sets. With no candidate above the minimum, the stop waits for approval. One threat raises alerts in many groups, so a node or volume under threat gets at most one autonomous stop until the owner replies in that stop's thread, checked in the transaction that writes the Write record row (`shape.md`). A stop that relieves nothing is then not followed by the next candidate. The approval path ignores the label, since the owner picks that target. The agent's report names the unlabeled workloads in allowlisted namespaces, so a missing label shows up in Discord. Rejected: an `essential` label that marks what to keep, because a new application would be stoppable until labeled; a separate list file, because it drifts from the manifests; the model picking the target, because injected text could steer it.
- **GitOps repositories: a list**: the infrastructure behind the cluster can span several repositories, such as one for the hypervisor hosts, one for the platform and one for the workloads. The deployment lists them, the first being the default, and the agent reads and files issues on each one. Which repositories they are stays in the deployment, outside this repository. What each holds is written in the operating instructions, so the model knows where to look. Rejected: one GitOps repository, because a cause in the hosts or the platform would then sit outside what the agent reads.
- **Hand-off: issues, not pull requests**: the agent opens one issue per alert group on the listed repository that holds the root cause, and keeps its body current instead of adding a comment per turn. The body holds three sections: the symptom, the cause the agent found, and the actions it took. The conversation, the queries and the alert data stay in Discord and the store. The model names that repository from the list. Code checks the name, writes the body and holds the issue there for the session's life. With no repository named, the issue opens on the default. Injected text can then at most move an issue to another of the owner's listed repositories, and never changes its body or whether it is written. The actions section names each stopgap taken and its undo. The owner takes each issue and writes or delegates the fix. An agent given the fix works on that repository without the owner's cluster access. Rejected: the agent opening pull requests, because the owner's merge gates either path and a fix needs more context than a first responder holds; an agent that takes issues unattended, in CI or on a machine with the owner's cluster access, because issue bodies carry model text written from stranger text; every issue on one fixed repository, because the owner would then move each issue by hand to where its fix lands; a comment per turn holding the answer, queries and alert data, because the owner reads the issue for the fix, not the conversation.
- **Memory**: incident history is SQLite on the agent's volume. The agent reads the owner's notes through a read-only mirror and never writes them, so the notes keep one writer. Rejected: the agent writing the notes, because their sync spreads a write to every device at once with no revert.
- **Operating instructions**: markdown in a private repository, cloned to `INSTRUCTIONS_DIR` and read on each turn, so a new commit applies without a restart. Every file goes into the system prompt except the runbooks: `runbooks/<alertname>.md` goes in only on a turn of that alert group, picked by matching the clone's file names, so an alertname never builds a path. While the clone is missing, a turn runs on the base instructions and the owner hears of it once a day, so a broken sync never fails every turn. The owner edits them with Claude Code on the subscription instead of the API. Rejected: the agent's own store edited through an MCP server, because history and revert would need building; every runbook on every turn, because each step resends them all; an index the model reads files from through a tool, because the model can skip a file it needs and each read adds a step.
- **Deployment**: a Helm chart in this repository's `chart/`, with its values in the cluster's private GitOps repository. Namespace names, the allowlist and in-cluster URLs live in the values. The chart makes one RoleBinding per allowlisted namespace from a list. The values pin the chart to a release tag and the image to its digest, so a chart change, which carries the agent's RBAC and admission policies, reaches the cluster only through a commit to the GitOps repository. Each push to main makes that commit itself: the workflow tags the release, pushes its image, and writes both pins through the homelab CI GitHub App, whose token reaches that one repository. What stands before the cluster is the `coding-review` pass that `CLAUDE.md` requires before a push that changes the chart. Rejected: Kustomize, because it needs a file per allowlisted namespace, and the RBAC layout a chart shows is already public in this document.
- **Image**: a GitHub-hosted runner builds it and pushes to GHCR, and the cluster pulls it through its registry's pull-through cache. Each push to main is a release: semantic-release takes the next version from the Conventional Commits since the last `v*` tag (`releaserc.toml`), `feat` bumping minor and every other type patch, and the image carries that version. Tags are the only version source, so no file holds the version. Rejected: an in-cluster runner, because a public repository's pull request workflows would run inside the cluster network.
- **Spend guard**: a per-turn cap and a monthly cap in USD. A turn is the agent's answer to one notification or one owner reply. The cap is per turn, not per session, because a session lives as long as its alert group recurs, so a lifetime cap would mute the group for good. A repeat notification whose firing alerts are unchanged starts no turn. At the monthly cap the agent stops calling models until the month turns (UTC) and says so once in Discord, while alerts still reach Discord directly. The monthly cap stays under the owner's Anthropic credit.
- **Durable turns in SQLite**: a turn survives a restart or a failed model call, so a change in an alert group is never dropped. The queue lives in the same SQLite file as the sessions and the spend. Rejected: the cluster's shared PostgreSQL, because the agent would fail with the database it guards.
- **Metrics: Prometheus scrape**: the agent serves `/metrics` on its own port for the cluster's Prometheus, so the spend record outlives the SQLite file in the metrics store's retention. Spend is two counters labeled by model, what the middleware reserves before each call and what it refunds after, so reserved less refunded is what the store charged, a call cut by a crash included. Per-turn spend, duration and tokens are histograms, and turns and tool calls are counters labeled by how the turn ended and by tool name. Labels take only values from a fixed set: model, turn end and tool name. Session, alert name and namespace never become labels, since each new alert group would add series; per-session detail stays in the logs. Grafana shows the series, and an alert rule can warn as the month's spend nears its cap. The NetworkPolicy then admits the Prometheus scraper to the metrics port, which serves no webhook. The turn histograms are observed when a turn ends, done or stopped by its cap: spend over all its attempts, duration and tokens of the attempt that ended it. The chart makes a PodMonitor only with a scraper selector, which the NetworkPolicy rule needs too. Rejected: spend in the turn's log line read through LogQL, because an alert on the month's running total would recompute it from logs.
- **SQLite durability: Litestream to R2**: a Litestream sidecar replicates the SQLite file to a Cloudflare R2 bucket within seconds of each write, and an init container restores the newest copy before the agent starts, so a deleted PV or a lost pool costs seconds of state. Only a missing file is restored: a corrupt one stays until the owner deletes it together with its `-wal`, `-shm` and `.<file>-litestream` neighbours, since a leftover WAL would replay onto the restored copy. The sidecar only logs a failed upload and the pod stays Ready, so its metrics are scraped with the agent's, and an alert rule warns when syncs or uploads keep failing for 15 minutes, before an old copy is all a restore could bring back. The bucket holds this file alone, and its token reaches only that bucket. The token and the endpoint come from the secret store, and egress admits the R2 endpoint. Only the two Litestream containers hold the token, never the agent's own. The restore runs as an init container that exits cleanly when the file exists or the bucket holds no copy yet, and the replication as a native sidecar, which starts before the agent and stops after it, so the last writes reach the bucket. The store runs in WAL mode, which Litestream replicates. Without it a lost file resets the month's spend, which lets the agent spend up to another monthly cap, drops queued turns, posts and hand-offs, and orphans each session's issue. Due before the stopgap tools, since the Write record and approvals live in the same file. Rejected: snapshots of the volume, because the cluster has no VolumeSnapshot support and no host-side snapshot of CSI volumes; the cluster's own object store, because it sits on the same host as the volume.
- **Spend seed after a lost file**: when the agent starts on a new SQLite file that no restore filled, it seeds the month's spend from its own spend counters in the metrics store, filtered to its own scrape job. Each pod is a new series whose first scrape can already hold a turn's spend, which `increase()` drops, so the seed takes each series' last value in the month less its value at the month's start, or the whole value for a series born in the month, and sums reserved less refunded. A raised seed stops model calls early, which fails safe, while alerts still reach Discord directly. A failed query seeds zero and tells the owner once. A file is new when it is missing as the agent starts, after the restore has run. The transaction that makes its tables marks it as waiting for the seed, and the seed or a failed read ends the wait, so a start cut before the seed seeds on the next one. The seed runs before any turn, and reads the job the chart names from its PodMonitor, with partial answers refused, since Thanos Query otherwise answers with the stores still up. It reads each series' raw samples over the month and sums their rises, a drop counting as a reset, so the metrics store must keep raw samples for a month. A refunded series counts only against the reserved series with the same labels, and each pair counts at least zero, and a series holding a value no counter can hold is left out, so a written series can only raise the seed. Spend in a pod's last seconds before its final scrape is never counted. Rejected: trusting the metrics store's value as is, because a forged low value would lift the cap.
