# Design

ops-agent is the first responder for one Kubernetes cluster and its one owner. Chosen holds the owner's decisions, Shape the mechanism behind them, and Open the decisions still due. Take an Open item to the owner before building it.

## Chosen

- **Role: operator, not engineer**: the agent contains an incident and hands off the cause. It protects, in order, data, then security, then service, and may stop a service that threatens the cluster. A manifest change, a resource limit included, belongs to the owner, who takes the issue. Rejected: HolmesGPT as the base, because it carries investigation through its own scripts and analysis further than a first responder needs, and its approval flow targets Slack.
- **Long-running and conversational**: a Deployment that holds one session per alert group and continues it when the owner replies in the alert's Discord thread. Rejected: one `claude -p` run per alert on CI runners, because it ends before the owner can answer.
- **Owner channel**: Discord only, through threads and approval buttons. The bot posts a starter message in one configured channel and opens the alert group's thread on it. The bot reaches Discord through `@discordjs/core`, `@discordjs/ws` and `@discordjs/rest`. Rejected: a dedicated web front end, because Discord already carries the alerts, the conversation and the buttons; a thread on Alertmanager's own message, because finding that message means matching titles that carry stranger text; a hand-written gateway client, because a silent disconnect would cut the owner channel unseen.
- **Provider-neutral**: the loop calls models through the Vercel AI SDK, which reaches Anthropic directly, OpenRouter, and OrcaRouter, the last two through the OpenAI API. Anthropic is paid from the owner's monthly API credit. Rejected: a subscription token from `claude setup-token`, because Anthropic's terms cover "ordinary, individual usage" and say nothing on unattended runs; pi-ai, because the SDK reaches all three providers through maintained packages.
- **Runtime**: TypeScript on Bun, in this public repository, separate from the owner's data. The loop, session store and context compaction are built here, not inherited from Claude Code.
- **Trigger**: every alert with severity `warning` or `critical` starts or resumes a session.
- **Stopgap autonomy**: the agent acts without approval only when its own PromQL reads show a cluster-wide threat: a node pressure condition held for 2 minutes, a node NotReady for 5 minutes, or shared storage at 90% used, or at 80% used and on a 6-hour trend that fills it within 6 hours. The 80% floor keeps one short write burst on a mostly empty volume from starting a stop. Every other stopgap waits for the owner's approval button in the thread. The threat test reads only metrics the agent queried, never alert annotations or log text, so injected text cannot start a stop. Code, not the model, also picks an autonomous stop's target (Autonomous targets). Rejected: full autonomy, because a misread or injected stop takes a service down unseen; approval for every stop, because the cluster goes unguarded while the owner sleeps.
- **Stopgap actions**: scale a Deployment or StatefulSet to zero, suspend a CronJob, delete a Pod so its controller restarts it. Each keeps the PVCs and one reverse action undoes it, so the worst case of a wrong stop is downtime. The agent does not undo its own stopgap: the issue records the undo, and the owner approves it in the thread.
- **Stoppable namespaces: an allowlist**: a namespace is stoppable only once the owner adds it, so a new application stays protected until then. The allowlist never holds a namespace that stores or backs up data for others, such as the shared database and its operator, or one that runs the platform: the GitOps controller, secret sync, monitoring, storage drivers, `kube-system`, and the agent's own. When the database is under threat, the agent stops the applications writing to it, never the database. The allowlist lives in the deployment, outside this repository. Rejected: a denylist, because a new platform component missing from it would be stoppable.
- **Autonomous targets: an opt-in label**: in an allowlisted namespace, a workload is a candidate for an autonomous stop only when its manifest carries the `stoppable` label. The label key carries a prefix whose domain the deployment sets, takes one exact value, and is read from the live Deployment, StatefulSet or CronJob, never from a pod. Code measures each candidate's share of the threat with PromQL, such as its memory on the pressured node or its writes to the filling volume, and stops the largest above a minimum share of 20%. That value is unmeasured (candidates). Share comes only from kubelet, cAdvisor and node-exporter series, since an application's own metrics can carry labels it sets. With no candidate above the minimum, the stop waits for approval. One threat raises alerts in many groups, so a node or volume under threat gets at most one autonomous stop until the owner replies in that stop's thread, checked in the transaction that writes the Write record row. A stop that relieves nothing is then not followed by the next candidate. The approval path ignores the label, since the owner picks that target. The agent's report names the unlabeled workloads in allowlisted namespaces, so a missing label shows up in Discord. Rejected: an `essential` label that marks what to keep, because a new application would be stoppable until labeled; a separate list file, because it drifts from the manifests; the model picking the target, because injected text could steer it.
- **GitOps repositories: a list**: the infrastructure behind the cluster can span several repositories, such as one for the hypervisor hosts, one for the platform and one for the workloads. The deployment lists them, the first being the default, and the agent reads and files issues on each one. Which repositories they are stays in the deployment, outside this repository. What each holds is written in the operating instructions, so the model knows where to look. Rejected: one GitOps repository, because a cause in the hosts or the platform would then sit outside what the agent reads.
- **Hand-off: issues, not pull requests**: the agent opens one issue per alert group on the listed repository that holds the root cause, and keeps its body current instead of adding a comment per turn. The body holds three sections: the symptom, the cause the agent found, and the actions it took. The conversation, the queries and the alert data stay in Discord and the store. The model names that repository from the list. Code checks the name, writes the body and holds the issue there for the session's life. With no repository named, the issue opens on the default. Injected text can then at most move an issue to another of the owner's listed repositories, and never changes its body or whether it is written. The actions section names each stopgap taken and its undo. The owner takes each issue and writes or delegates the fix. An agent given the fix works on that repository without the owner's cluster access. Rejected: the agent opening pull requests, because the owner's merge gates either path and a fix needs more context than a first responder holds; an agent that takes issues unattended, in CI or on a machine with the owner's cluster access, because issue bodies carry model text written from stranger text; every issue on one fixed repository, because the owner would then move each issue by hand to where its fix lands; a comment per turn holding the answer, queries and alert data, because the owner reads the issue for the fix, not the conversation.
- **Memory**: incident history is SQLite on the agent's volume. The agent reads the owner's notes through a read-only mirror and never writes them, so the notes keep one writer. Rejected: the agent writing the notes, because their sync spreads a write to every device at once with no revert.
- **Operating instructions**: markdown in a private repository, cloned to `INSTRUCTIONS_DIR` and read on each turn, so a new commit applies without a restart. Every file goes into the system prompt except the runbooks: `runbooks/<alertname>.md` goes in only on a turn of that alert group, picked by matching the clone's file names, so an alertname never builds a path. While the clone is missing, a turn runs on the base instructions and the owner hears of it once a day, so a broken sync never fails every turn. The owner edits them with Claude Code on the subscription instead of the API. Rejected: the agent's own store edited through an MCP server, because history and revert would need building; every runbook on every turn, because each step resends them all; an index the model reads files from through a tool, because the model can skip a file it needs and each read adds a step.
- **Deployment**: a Helm chart in this repository's `chart/`, with its values in the cluster's private GitOps repository. Namespace names, the allowlist and in-cluster URLs live in the values. The chart makes one RoleBinding per allowlisted namespace from a list. The values pin the chart to a tag or commit, so a chart change, which carries the agent's RBAC and admission policies, reaches the cluster only through a commit to the GitOps repository. Rejected: Kustomize, because it needs a file per allowlisted namespace, and the RBAC layout a chart shows is already public in this document.
- **Image**: a GitHub-hosted runner builds it and pushes to GHCR, and the cluster pulls it through its registry's pull-through cache. Rejected: an in-cluster runner, because a public repository's pull request workflows would run inside the cluster network.
- **Spend guard**: a per-turn cap and a monthly cap in USD. A turn is the agent's answer to one notification or one owner reply. The cap is per turn, not per session, because a session lives as long as its alert group recurs, so a lifetime cap would mute the group for good. A repeat notification whose firing alerts are unchanged starts no turn. At the monthly cap the agent stops calling models until the month turns (UTC) and says so once in Discord, while alerts still reach Discord directly. The monthly cap stays under the owner's Anthropic credit.
- **Durable turns in SQLite**: a turn survives a restart or a failed model call, so a change in an alert group is never dropped. The queue lives in the same SQLite file as the sessions and the spend. Rejected: the cluster's shared PostgreSQL, because the agent would fail with the database it guards.
- **Metrics: Prometheus scrape**: the agent serves `/metrics` on its own port for the cluster's Prometheus, so the spend record outlives the SQLite file in the metrics store's retention. Spend is two counters labeled by model, what the middleware reserves before each call and what it refunds after, so reserved less refunded is what the store charged, a call cut by a crash included. Per-turn spend, duration and tokens are histograms, and turns and tool calls are counters labeled by how the turn ended and by tool name. Labels take only values from a fixed set: model, turn end and tool name. Session, alert name and namespace never become labels, since each new alert group would add series; per-session detail stays in the logs. Grafana shows the series, and an alert rule can warn as the month's spend nears its cap. The NetworkPolicy then admits the Prometheus scraper to the metrics port, which serves no webhook. The turn histograms are observed when a turn ends, done or stopped by its cap: spend over all its attempts, duration and tokens of the attempt that ended it. The chart makes a PodMonitor only with a scraper selector, which the NetworkPolicy rule needs too. Rejected: spend in the turn's log line read through LogQL, because an alert on the month's running total would recompute it from logs.
- **SQLite durability: Litestream to R2**: a Litestream sidecar replicates the SQLite file to a Cloudflare R2 bucket within seconds of each write, and an init container restores the newest copy before the agent starts, so a deleted PV or a lost pool costs seconds of state. Only a missing file is restored: a corrupt one stays until the owner deletes it together with its `-wal`, `-shm` and `.<file>-litestream` neighbours, since a leftover WAL would replay onto the restored copy. The sidecar only logs a failed upload and the pod stays Ready, so its metrics are scraped with the agent's, and an alert rule warns when syncs or uploads keep failing for 15 minutes, before an old copy is all a restore could bring back. The bucket holds this file alone, and its token reaches only that bucket. The token and the endpoint come from the secret store, and egress admits the R2 endpoint. Only the two Litestream containers hold the token, never the agent's own. The restore runs as an init container that exits cleanly when the file exists or the bucket holds no copy yet, and the replication as a native sidecar, which starts before the agent and stops after it, so the last writes reach the bucket. The store runs in WAL mode, which Litestream replicates. Without it a lost file resets the month's spend, which lets the agent spend up to another monthly cap, drops queued turns, posts and hand-offs, and orphans each session's issue. Due before the stopgap tools, since the Write record and approvals live in the same file. Rejected: snapshots of the volume, because the cluster has no VolumeSnapshot support and no host-side snapshot of CSI volumes; the cluster's own object store, because it sits on the same host as the volume.
- **Spend seed after a lost file**: when the agent starts on a new SQLite file that no restore filled, it seeds the month's spend from its own spend counters in the metrics store, filtered to its own scrape job. Each pod is a new series whose first scrape can already hold a turn's spend, which `increase()` drops, so the seed takes each series' last value in the month less its value at the month's start, or the whole value for a series born in the month, and sums reserved less refunded. A raised seed stops model calls early, which fails safe, while alerts still reach Discord directly. A failed query seeds zero and tells the owner once. A file is new when it is missing as the agent starts, after the restore has run. The transaction that makes its tables marks it as waiting for the seed, and the seed or a failed read ends the wait, so a start cut before the seed seeds on the next one. The seed runs before any turn, and reads the job the chart names from its PodMonitor, with partial answers refused, since Thanos Query otherwise answers with the stores still up. It reads each series' raw samples over the month and sums their rises, a drop counting as a reset, so the metrics store must keep raw samples for a month. A refunded series counts only against the reserved series with the same labels, and each pair counts at least zero, and a series holding a value no counter can hold is left out, so a written series can only raise the seed. Spend in a pod's last seconds before its final scrape is never counted. Rejected: trusting the metrics store's value as is, because a forged low value would lift the cap.

## Shape

- **Inputs**: an Alertmanager webhook receiver beside the owner's Discord receivers, and a Discord bot that reads replies in the threads it opened. Alert delivery to Discord does not go through the agent, so the agent being down loses no alert. Every webhook request carries a bearer token. Nothing outside the cluster reaches the agent: the Discord bot, GitHub and the model APIs are outbound calls, so it has no route from outside, and a NetworkPolicy admits ingress from Alertmanager alone. Egress is limited the same way: cluster DNS, the API server, the PromQL endpoint, Loki, and the HTTPS hosts of Discord, GitHub, the model providers and the R2 bucket, the external ones through the CNI's FQDN rules. The agent's own connections then reach no other host. Discord and GitHub still fetch links in what the agent posts, so posting follows the link rule in Threat model.
- **Session**: one alert group (`alertname`, `namespace` from `groupLabels`) maps to one Discord thread, one session and one issue. A reply in the thread from the owner's ID queues a turn on that session. Button presses and replies arrive over the gateway, so no interactions endpoint takes requests from outside.
- **Posts**: the transaction that ends a turn also queues its post to the owner, and one outbox sends queued posts in order. A post that fails for a passing reason stays queued and resumes after its last sent message, a post Discord refuses with a 4xx is dropped, and a post to a deleted thread opens a new one. The starter message is recorded before its thread opens, so a retry opens the thread on it instead of posting another. The gateway connects in the background, so a Discord outage at start leaves the webhook up. A turn ended by the attempt limit posts in its thread, and the monthly cap posts once a month in the channel. While a turn runs on a session that has a thread, the bot shows typing in it every 8 seconds, and a failed typing call is ignored.
- **Issues**: code, not a tool, writes the hand-off. The transaction that ends a turn with any finished step also queues its hand-off. The model fills the three sections through a tool that only records them, and the turn's last call wins. A turn with no call still hands off: code writes the symptom from the alert group's name and firing alerts, the answer as the cause, and no actions. A turn stopped before its answer with no call hands off only while the session has no issue, so a cut turn never replaces a cause found earlier. The actions section comes from the Write record once the stopgap tools exist, so the model never claims an action that did not run. One queue writes hand-offs in order: a session's first opens its issue and later ones replace its body, which GitHub keeps in the edit history. A write that fails for a passing reason, a 401, a rate limit or a 5xx stays queued, any other 4xx drops it, and an edit of a deleted issue opens a new one. Each session's issue carries a marker, so a retry after a lost response finds the issue instead of opening another. Each section loses links off `LINK_ALLOWLIST`, and character references break whatever could still form a link, image, HTML tag or heading. A heading in model text could fake the Actions section. The references apply inside the model's own code too, where they show literally, since telling code from text exactly takes a markdown parser. Each section is cleaned whole and then cut to its size, so the body stays under GitHub's limit. A turn's hand-off carries the repository the model last named in that turn through the same kind of record-only tool. The session's first write fixes the issue's repository, so later names are ignored, and an issue reopened after a deletion opens on the same repository. Each write's installation token is scoped to issues write on that one repository. Rejected: a tool the model calls to write the issue, because injected text could then hold back the hand-off or rewrite it.
- **Turn queue**: one process runs every session, with no scheduler or workers. Turns on one session run in order, and turns on different sessions run in parallel up to a global limit. Each step has a time limit, so a stalled model call fails its attempt instead of holding a slot. The firing record and the pending turn are written in one transaction, and the turn's messages and its completion in another. An attempt starts with a transaction that raises the attempt count and sets the next attempt time, so a turn that crashes the process counts too. A failed turn stays pending and runs again once its next attempt time passes, in this process or after a restart. The turn's spend is stored with it, charged at each call's reservation and carried across attempts, so retries share one per-turn cap and a call cut by a crash stays charged at its worst case. A monthly-cap refusal before any step finishes leaves the turn pending without spending an attempt. A per-turn cap refusal ends the turn, and so does the attempt limit, after which the agent says so once in the thread. Turns behind a failed one wait only until it ends.
- **Context compaction**: the store keeps every message whole, and each turn rebuilds the history it sends, so a change of threshold applies to every session at its next turn. Size is UTF-8 bytes of the stored messages. Past the mask threshold, tool results from the oldest turns go as a short marker until the history fits, and the newest turn keeps its output. Past the higher summary threshold, after masking, a summary replaces the oldest turns, which brings the rest to half that threshold. The newest turn is never summarized. A summary is stored with the last message it covers and builds on the one before it. A turn uses no summary when the history fits, or else the oldest stored summary whose later turns fit, and makes a new one only when none does. The summary call goes through the spend middleware, charged to the turn. The summary reaches the model wrapped as data, since it is written from stranger text. History grown within one turn is not compacted. Rejected: summary alone, because coding-agent benchmarks measured masking first as the cheapest order at an equal success rate.
- **Write record**: a turn appends its messages only at its end, so a rerun turn cannot see what an earlier attempt did. Before a write's API call, code commits a row holding the tool, the resolved target and the approval, and marks that approval used in the same transaction. The row is marked done after the call. On a rerun, a done row returns its recorded result, and a row not marked done follows the timeout rule in Tool contract. The autonomous stop returns its recorded target and never picks again. Approvals live in the same SQLite file, so one given while a turn waits survives a restart. An approval belongs to the turn that asked for it and is void once that turn ends.
- **Tools**, each a fixed function, no shell:
  - Kubernetes reads through a ServiceAccount bound to ClusterRole `view`, which excludes Secrets, Roles and RoleBindings. `view` also lacks core `nodes`, `persistentvolumes` and `storageclasses`, so a second ClusterRole grants `get`, `list` and `watch` on those. One tool reads an object in full without its managed fields and last-applied configuration. The other lists a kind as the table the API server renders for `kubectl get`. Both take kinds from a fixed set that leaves out Secrets and ConfigMaps. A third reads one container's log, current or previous, through `pods/log`, which `view` grants. It takes the last lines up to 500 and keeps the last 20,000 characters, so the contract's cut, which keeps the start, never drops the newest lines. Log text is stranger text and passes the same redaction and wrapping as other tool output.
  - PromQL against an endpoint that serves recent and long-retention data together, and LogQL against Loki.
  - Read and search of a clone of each listed GitOps repository at `main`, each kept current by its own sync sidecar with the GitHub App's contents read. A call names its repository from the list. A read resolves the clone's root on each call and stays inside it and outside `.git`.
  - The three stopgap actions, in allowlisted namespaces only, each taking a target and waiting for approval.
  - An autonomous stop that takes no target: code runs the threat test and picks the target (Chosen, Autonomous targets).
- **Tool contract**: each tool has a time limit, 20 seconds unless the tool sets its own. A timeout, a failed call or a bad argument comes back to the model as a result that names what failed and a next step, and never ends the turn. Code checks arguments against the tool's schema, since the SDK's own check returns no next step. A result is redacted, wrapped in a `<tool_output>` element with `<` escaped, and cut at 30,000 characters. A write that timed out may have run, so it is not retried in that turn: its next step is to read the object and report the state to the owner. A turn that repeats an identical tool call gets no second run, and its next model call is made with tool choice `none`, so it answers. The tool list stays fixed for a session's life, so the stopgap tools are always offered. When one is called, code checks the allowlist. A targeted stop then needs an owner approval bound to that exact action (namespace, kind, name) and used once. The autonomous stop needs the threat test that code runs on the agent's own PromQL results. The model's claim of a threat never stands in for either.
- **Write boundary**: RBAC and admission policy enforce the stopgap limits, not the prompt. Each allowlisted namespace gets a RoleBinding for `deployments/scale`, `statefulsets/scale`, `patch` on `cronjobs`, and `delete` on `pods`. Those verbs reach past the stopgaps: a scale can raise replicas, a pod delete can remove a pod no controller restores, and a CronJob patch can rewrite the job template to run any ServiceAccount in the namespace. A ValidatingAdmissionPolicy therefore holds the agent's ServiceAccount to the stopgaps alone: a scale sets replicas to 0, a deleted pod has an owner reference, and a CronJob patch sets `spec.suspend: true` and leaves every other field the client sets unchanged, labels and annotations included.
- **Audit**: the API server's audit policy records the agent ServiceAccount's writes with request and response bodies, and its other requests as metadata. A rule that records Secrets and ConfigMaps at `Metadata` comes first, since the first matching rule sets the level, so no body of theirs reaches the audit log. An event belongs to the agent by its `user` field. `userAgent` is set by the client and proves nothing.
- **GitOps self-heal**: Argo CD with `selfHeal: true` reverts a scale to zero unless the Application pauses its sync. Pausing needs `patch` on the Application, and that verb can also repoint its source, which equals cluster-admin. A ValidatingAdmissionPolicy limits the agent's ServiceAccount to the pause field alone. Unverified: whether the ApplicationSet controller overwrites that field on the Applications it generates.
- **Credentials**, each from the cluster's secret store: the model API key, the webhook token, the Discord bot token, a GitHub App key, and the R2 token, which only the Litestream containers read. The App holds contents read and issues write, and its one installation covers every listed GitOps repository and the instructions repository. The App's permissions apply to every repository the installation covers, so the agent scopes each issue token down to issues write on one listed repository. A sync sidecar's token reads every covered repository, which stays read-only. The Discord bot holds View Channel, Send Messages, Create Public Threads, Send Messages in Threads, Read Message History and Manage Threads, plus the Message Content intent to read replies. Manage Threads archives a thread once its alert group resolves, and it also lets the bot lock or delete any thread in the channel. Rejected: a 60-minute auto-archive set at thread creation, because it also hides a quiet group that still fires. Only the owner's Discord user ID is a command source, and an approval is a button press from that ID, never model text.
- **Spend enforcement**: every model call goes through one middleware that checks the call's worst case against the turn's running total and reserves it against the month's spend in SQLite before the call, then settles to the reported cost after. The worst case is the UTF-8 bytes of the prompt and tool definitions plus a fixed allowance as input, and `max_tokens` as output. Measured on Claude Sonnet 5.5: with `count_tokens`, a one-turn history of 3,890 bytes, holding a thinking signature, counts 1,010 input tokens. In real three-step tool loops that resent up to 477 thinking tokens, the API reported 0.40-0.46 input tokens per prompt byte. A call refused by the API with a status of 400 or above is refunded, and any other failure keeps its reservation. A reservation refused mid-turn ends the turn and keeps the steps already finished, since a tool they ran may have changed the cluster. The month's spend and the turn queue live in one SQLite file, so the agent runs as one replica with the `Recreate` strategy. The model's price comes from a table keyed by model ID, or from all four `PRICE_*` variables when set. A model in neither stops the start.

## Threat model

- This repository is public. Hostnames, addresses, the cluster's namespace names, secret paths, the names and contents of the owner's private repositories, and anything from the owner's notes stay out of code, fixtures, docs and commits.
- Alert labels and annotations, log lines and tool output can carry text set by strangers, such as titles from a downloader's logs. They are data. No tool executes a command taken from that text. Rendered text is wrapped and escaped before it reaches the model, labels and annotations are cut to a fixed size, and the request body is capped at 1 MB, and an issue body that quotes it is data to whoever takes the issue.
- Any pod in the cluster can reach the agent's Service. The webhook token holds even when the NetworkPolicy is missing.
- Spend that escapes the caps is a defect. So is a model call path that bypasses the spend middleware.
- The agent's environment holds only the credentials listed in Shape. Tool output is redacted before it reaches the model or a log, and model replies before they reach logs, Discord or GitHub, since `view` can read pod specs and ConfigMaps. Redaction replaces known token formats, private key blocks, a block cut before its end to the text's end and one cut before its start from the text's start, URL passwords, bearer credentials and values under keys that end in a secret's name, and by field every env value and every value in a Secret manifest. A bare secret under an innocent key passes it, and so does the part of a secret after a backslash. Cluster state that passes redaction, such as object names, events and log lines, goes to the model provider. That exposure is accepted.
- The threat test and the target choice trust the metrics store, so a pod that writes series into it could fake a threat or pick the target. Autonomous stops stay off until the deployment confirms the store's write paths are closed to applications: the store takes pushed series from no one, or from the scrapers alone through a NetworkPolicy, and an admission policy denies `honor_labels` on application scrapes.
- Injected text can ask the model to put cluster state into a URL. Discord's link embeds and GitHub's image proxy fetch such a URL from outside the cluster, past the egress rules. So the agent posts to Discord with embeds suppressed, and strips links and images whose host is off an allowlist from Discord messages and issue bodies. The allowlist holds consoles the owner reads, such as dashboards, the metrics store and the GitOps controller. It never holds a service that fetches a URL it is given or redirects to one, such as a downloader or a login server, since a link to it carries data on to any host.
